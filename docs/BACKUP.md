# Резервные копии и восстановление

## Что и когда

Контейнер `backup` (`server/backup`) раз в сутки в `BACKUP_TIME` (по умолчанию
03:30 мск) и сразу при запуске снимает копию:

| Что | Зачем |
|---|---|
| база Postgres (`pg_dump -Fc`) | аккаунты, подписки, платежи, книги, журналы |
| `data/rustdesk` — **ключ сервера `id_ed25519`** и данные hbbs | без ключа ни один установленный клиент не подключится к новому серверу |
| `data/attachments` | снимки экрана из обращений |
| `data/releases` (если `BACKUP_RELEASES=true`) | загруженные сборки; обычно их проще собрать заново |

Каждая копия:

1. **шифруется** паролем `BACKUP_PASSPHRASE` (AES-256, PBKDF2, 200 000 итераций);
2. **проверяется восстановлением**: контейнер разворачивает базу во временном
   Postgres, сверяет число пользователей с оригиналом, проверяет контрольные
   суммы всех файлов и наличие ключа сервера. Копия, которую не удалось
   развернуть, считается неудачной;
3. **уходит во внешнее хранилище** (S3-совместимое: Yandex Object Storage,
   Selectel, VK Cloud) — копия на том же сервере не спасёт, если пропадёт сервер;
4. хранится локально `BACKUP_KEEP_DAYS` дней (по умолчанию 14) в `server/backups`.

Итог каждой копии приходит в мониторинг сайта. Нет проверенной копии за 26 часов
или копия не удалась — тревога в Telegram и на почту. Копия лежит только на
этом сервере — предупреждение (админка → «Мониторинг» → «Резервные копии»).

## Настройка

В `server/.env` (скрипт развёртывания создаёт пароль сам):

```env
BACKUP_PASSPHRASE=...            # сохраните в менеджере паролей: без него копии не расшифровать
BACKUP_TIME=03:30
BACKUP_KEEP_DAYS=14
BACKUP_RELEASES=false

# Внешнее хранилище (пример — Yandex Object Storage)
BACKUP_S3_ENDPOINT=https://storage.yandexcloud.net
BACKUP_S3_REGION=ru-central1
BACKUP_S3_BUCKET=remit-backups
BACKUP_S3_PREFIX=remit
BACKUP_S3_ACCESS_KEY=...
BACKUP_S3_SECRET_KEY=...
```

Для хранилища:

- заведите **отдельный** бакет и сервисный аккаунт с правом только на запись и
  чтение объектов в нём (в Yandex Cloud — роль `storage.uploader` и
  `storage.viewer` на бакет); не используйте ключи с доступом ко всему облаку;
- включите **правило жизненного цикла**: удалять объекты старше 60–90 дней;
- по возможности включите версионирование или блокировку объектов (object
  lock) — тогда взлом сервера не позволит стереть копии.

Без `BACKUP_PASSPHRASE` копии во внешнее хранилище не отправляются.

## Команды

```bash
cd server
docker compose --env-file .env exec backup remit-backup run            # копия сейчас
docker compose --env-file .env exec backup remit-backup verify /backups/remit-20260929-033000.tar.enc
docker compose --env-file .env run --rm backup fetch remit-20260929-033000.tar.enc   # скачать из хранилища
ls server/backups                                                     # локальные копии
```

## Восстановление

На том же или новом сервере (на новом — сначала `server/deploy.sh`, затем
перенесите в `server/.env` прежние `POSTGRES_PASSWORD`, `REMIT_AUTH_SECRET`,
`JWT_KEY`, `REMIT_SERVICE_TOKEN`, `BACKUP_PASSPHRASE` и `BACKUP_S3_*`):

```bash
sudo bash server/backup/restore.sh remit-20260929-033000.tar.enc
```

Скрипт:

1. берёт копию из `server/backups` или скачивает её из внешнего хранилища;
2. проверяет её (расшифровка, суммы, пробное развёртывание);
3. спрашивает подтверждение и сохраняет текущие данные в
   `server/backups/before-restore-*`;
4. останавливает сайт и hbbs, заменяет базу целиком, возвращает ключ сервера и
   вложения, запускает всё обратно.

После восстановления проверьте вход на сайте и в клиенте, страницу `/status` и
«Мониторинг» в админке. `REMIT_AUTH_SECRET` и `JWT_KEY` должны быть прежними:
от первого зависят зашифрованные секреты (токены ретрансляторов, пароли гостевых
ссылок), от второго — входы в клиенте.

## Раз в квартал

Проверка восстановления идёт с каждой копией, но полный прогон на чистой машине
раз в квартал — хорошая привычка: разверните сервер из `deploy.sh`, восстановите
последнюю копию из хранилища и убедитесь, что клиент подключается.
