# Сервер обновлений и рассылка настроек

Два разных механизма решают одну задачу — «правка доехала до всех клиентов»:

| Что нужно | Механизм | Скорость |
|---|---|---|
| Новая версия программы | сервер обновлений: клиент проверяет версию и ставит новую | по действию пользователя |
| Изменить настройку на всех клиентах | политика клиентов: сервер рассылает настройки в ответе heartbeat | до 15 секунд |

## 1. Сервер обновлений

### Что видит пользователь

При каждом запуске клиент спрашивает наш сервер о последней версии. Если она
новее установленной, в главном окне появляется карточка:

```text
Доступна новая версия RemIT (1.4.2).   [Обновить]  Журнал изменений
```

Кнопка «Обновить» на установленных Windows и macOS скачивает файл с нашего
сервера, показывает полосу загрузки и запускает установку поверх текущей
версии. В остальных случаях кнопка открывает страницу загрузок.

### Как это работает

Проверка: клиент отправляет `POST` на адрес проверки и получает
`{"url": "..."}`. Версию он берёт из **последнего сегмента адреса** и
сравнивает со своей.

Загрузка: нажав «Обновить», клиент заменяет в этом адресе `tag` на `download`,
сам дописывает имя файла сборки (`rustdesk-1.4.2-x86_64.exe`, `.msi` или
`.dmg`) и качает его. Поэтому сервер отвечает адресом такого вида:

```text
https://remit.su/obnovlenie/tag/1.4.2
```

и раздаёт файлы по `/obnovlenie/download/1.4.2/<имя файла>`: маршрут смотрит на
расширение и архитектуру в запрошенном имени и перенаправляет на нужный файл
выпуска. Имена файлов в вашем хранилище при этом любые — сопоставление идёт по
расширению и архитектуре, а не по имени.

Человеку адрес `/obnovlenie/tag/1.4.2` перенаправляет на обычную страницу
выпуска `/obnovlenie/1.4.2` с описанием изменений и кнопками загрузки.

### Публикация выпуска

Админка → **Обновления**:

1. версия (`1.4.2`), канал (`stable` или `beta`), признак обязательности;
2. что изменилось — одна строка на пункт;
3. для каждой платформы: ОС, архитектура и **кнопка «Загрузить файл»** —
   сборка уходит на ваш сервер прямо из браузера, с полосой прогресса;
   размер и SHA-256 считаются на сервере и подставляются сами;
4. «Опубликовать выпуск» — или «Сохранить черновиком», пока файлы не готовы.

Черновик не виден ни в проверке обновлений, ни на странице загрузок, ни по
прямому адресу выпуска (404).

### Где лежат загруженные файлы

```text
server/data/releases/<версия>/<имя файла>
```

Каталог задаётся переменной `REMIT_RELEASES_DIR` (в контейнере —
`/app/data/releases`, снаружи это `server/data/releases`) и подключён томом,
поэтому переживает пересоздание контейнера. Раздаются файлы с вашего домена:

```text
https://remit.su/api/download/1.4.2/RemIT-1.4.2-x64.exe
```

Загрузка идёт потоком на диск: файл не держится в памяти целиком, пишется во
временный файл и переименовывается только после полной записи — недокачанная
сборка к клиентам не попадёт. Предел размера — `REMIT_MAX_UPLOAD_BYTES`
(по умолчанию 1 ГБ), в nginx для маршрута загрузки поднят `client_max_body_size`.

Удаление выпуска удаляет и его файлы. Каталог `server/data/releases` стоит
включить в резервное копирование вместе с базой.

Внешнее хранилище тоже поддерживается: вместо загрузки вставьте в поле адреса
прямую ссылку, а для запасной раздачи со стороннего CDN задайте
`REMIT_DOWNLOADS_BASE`.

Версия уникальна внутри канала — иначе два разных файла разъехались бы под
одним номером.

### Маршруты

| Маршрут | Кто вызывает | Ответ |
|---|---|---|
| `POST /api/version/latest` | клиент RustDesk | `{"url": "https://remit.su/obnovlenie/1.4.2"}` |
| `GET /api/v1/updates/check?os=&arch=&version=&channel=` | установщики, скрипты | версия, обязательность, заметки, прямая ссылка, SHA-256 |
| `GET /api/v1/updates/manifest?channel=stable` | страница загрузок, автоматизация | список опубликованных выпусков |
| `GET /obnovlenie/<версия>` | пользователь | страница выпуска с загрузками |

Проверка вручную:

```bash
curl -s -X POST https://remit.su/api/version/latest \
  -H "Content-Type: application/json" \
  -d '{"os":"windows","arch":"x86_64","typ":"rustdesk-client"}'

curl -s "https://remit.su/api/v1/updates/check?os=windows&arch=x86_64&version=1.4.0"
```

Идентификатор ОС приводится к семейству: `astra`, `ubuntu`, `debian`, `redos`
и другие дистрибутивы считаются `linux`, `darwin` — `macos`.

### Фирменная сборка

Из коробки фирменная сборка RustDesk обновления **не проверяет**: и в Rust, и
во Flutter стоят проверки «это custom client — выходим». Скрипт
`client/patches/brand-client.py` снимает оба запрета, прописывает наш адрес
проверки и разворачивает ссылки карточки на наш сайт:

| Файл | Что делает патч |
|---|---|
| `libs/hbb_common/src/lib.rs` | адрес проверки обновлений — наш сервер |
| `src/common.rs` | снимает запрет проверки для фирменной сборки |
| `flutter/lib/common.dart` | включает проверку при запуске приложения |
| `flutter/lib/desktop/pages/desktop_home_page.dart` | показывает карточку обновления, ссылки ведут на наш сайт |
| `libs/hbb_common/src/config.rs` | `enable-check-update=Y` в настройках по умолчанию |

Команда:

```bash
python3 client/patches/brand-client.py /path/to/rustdesk \
  --app-name RemIT \
  --id-server remit.su \
  --api-server https://remit.su \
  --update-url https://remit.su/api/version/latest \
  --public-key "$(cat /opt/remit/data/rustdesk/id_ed25519.pub)"
```

### Тихое автообновление

Кроме предложения при запуске у клиента есть фоновый апдейтер: он проверяет
версию раз в сутки и, если включена настройка `allow-auto-update`, ставит
новую версию сам — но только когда нет активных сессий. Включается той же
политикой клиентов:

```json
{ "options": { "enable-check-update": "Y", "allow-auto-update": "Y" } }
```

Для парка машин это удобнее: обновление доезжает без участия пользователя.
Для частных клиентов лучше оставить предложение при запуске.

## 2. Политика клиентов: настройки для всех сразу

Клиент отправляет heartbeat каждые 15 секунд и присылает версию политики,
которую уже применил (`modified_at`). Наш шлюз сравнивает её со своей и при
отличии возвращает:

```json
{
  "modified_at": 1789806362122,
  "strategy": {
    "config_options": {
      "custom-rendezvous-server": "remit.su",
      "approve-mode": "password-click",
      "enable-check-update": "Y"
    }
  }
}
```

Клиент применяет настройки сам и запоминает версию — повторно она не
присылается. Переустанавливать ничего не нужно.

Где менять: админка → **Настройки** → «Настройки клиентов». Или через API:

```bash
curl -X POST https://remit.su/api/v1/admin/policy \
  -H "Authorization: Bearer $REMIT_SERVICE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"options":{"custom-rendezvous-server":"remit.su","approve-mode":"password-click"}}'
```

Частые ключи: адреса серверов (`custom-rendezvous-server`, `relay-server`,
`api-server`, `key`), проверка обновлений (`enable-check-update`), правила
доступа (`verification-method`, `approve-mode`), разрешения
(`enable-file-transfer`), запрет менять настройки на стороне пользователя
(`allow-remote-config-modification`).

Важно: политика применяется ко всем клиентам, которые смотрят на наш
API-сервер. Ошибочный адрес ID-сервера в политике уведёт клиентов на чужой
сервер — проверяйте значения перед рассылкой.

## Что стоит сделать дальше

- Подпись сборок и проверку подписи на стороне клиента.
- Постепенную выкатку: доля клиентов, которым предлагается новая версия.
- Политики для групп устройств, а не только общую для всех.
