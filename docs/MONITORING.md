# Мониторинг и страница статуса

## Что проверяется

Сайт проверяет всё, от чего зависит сервис, раз в минуту (`lib/monitoring.ts`,
запускается из `instrumentation.ts` при старте сервера):

| Проверка | Как | Как часто | Компонент на странице статуса |
|---|---|---|---|
| База данных | `SELECT 1` (или чтение файла) | 1 мин | Сайт и личный кабинет |
| Сервер ID (hbbs) | TCP к `rustdesk:21116` | 1 мин | Подключение к компьютерам |
| Ретрансляторы | TCP к каждому включённому узлу (основной — изнутри) | 1 мин | Ретрансляция |
| WebSocket hbbs и hbbr | TCP к `rustdesk:21118` и `:21119` | 1 мин | Веб-клиент |
| Сертификаты ретрансляторов | TLS на порт +2, срок действия | 1 ч | Веб-клиент (частичный сбой) |
| Сертификат сайта | TLS на `домен:443`, срок действия | 1 ч | — (только администратору) |
| ЮKassa | `GET /v3/me` — связь и ключи | 5 мин | Приём оплаты |
| Автопродление и чеки | ошибки последнего запуска | 10 мин | — |
| Почта | вход на SMTP-сервер | 15 мин | — |
| Диск | свободное место в каталогах данных | 10 мин | — |
| Резервные копии | есть проверенная копия не старше 26 ч, ушла во внешнее хранилище | 10 мин | — |

Состояние компонента — худшее из его проверок. Ретрансляция — исключение:
пока жив хоть один ретранслятор, соединения идут, и это «частичный сбой», а
не отказ.

## Оповещения

- **Когда:** сбой подтверждается двумя проверками подряд (чтобы не будить
  из-за одного потерянного пакета), восстановление — сразу. «Внимание»
  (сертификат истекает через 14 дней, мало места, ошибки автопродления) — один
  раз при появлении.
- **Куда:** Telegram (`REMIT_TELEGRAM_BOT_TOKEN` и `REMIT_ALERT_TELEGRAM_CHAT_ID`,
  по умолчанию тот же чат, что для заявок) и почта (`REMIT_ALERT_EMAILS`, по
  умолчанию `REMIT_ADMIN_EMAILS`; нужна настроенная почта).
- **Проверить канал:** админка → «Мониторинг» → «Тестовое оповещение».
- **Плановые работы** глушат оповещения по затронутым компонентам и не
  портят статистику доступности.

## Если лёг сам сайт

Сайт не может сообщить о собственном падении, поэтому есть два уровня защиты.

1. **Сторож** — контейнер `watchdog` (`server/monitor/watchdog.sh`). Раз в
   минуту запрашивает `http://web:3000/api/health`. После трёх провалов подряд
   шлёт тревогу в Telegram. Когда сайт ожил, шлёт «восстановлено» и передаёт
   сайту время простоя: оно попадает в доступность «Сайта» и в историю на
   странице статуса. Почту сторож не шлёт — только Telegram.
2. **Внешний мониторинг** — на случай, если лёг весь сервер вместе со
   сторожем. Подойдёт любой сервис проверки доступности (например, UptimeRobot,
   Яндекс Мониторинг, Better Stack, HetrixTools):
   - HTTP `https://<домен>/api/health` — 200, если сайт и база работают;
   - TCP `<домен>:21116` — сервер ID;
   - TCP `<домен>:21117` — ретранслятор;
   - для каждого отдельного ретранслятора — TCP `:21117`.

## Страница статуса

`https://<домен>/status` — публичная, ссылка в подвале сайта. На ней:

- общее состояние и состояние каждого компонента;
- доступность за 90 дней полосками по дням (на телефоне — за 30);
- текущие инциденты и плановые работы с хронологией;
- история инцидентов за две недели.

Адресов, текстов ошибок и имён узлов там нет — только то, что нужно
пользователям. То же в JSON — `GET /api/status`.

**Инциденты.** Когда компонент падает, мониторинг сам публикует инцидент «…:
нарушена работа» и сам закрывает его при восстановлении. Администратор может
добавить подробности («Причина найдена», «Наблюдаем») в админке → «Мониторинг».

**Плановые работы** объявляются там же: компоненты, начало и конец. Работы
сами начинаются и сами завершаются по расписанию. За сутки до начала и во
время работ в кабинете у пользователей висит баннер со ссылкой на
страницу статуса; во время сбоя — тоже.

## Хранение

- `monitor_days` — доступность по суткам (часовой пояс тарификации) для
  проверок и компонентов, хранится 100 дней;
- `monitor_events` — смены состояния, 100 дней;
- `incidents` — инциденты и работы;
- текущее состояние проверок — в `settings` (`monitor_state`).

## Настройка

```
REMIT_ALERT_EMAILS=            # куда слать сбои; пусто — REMIT_ADMIN_EMAILS
REMIT_ALERT_TELEGRAM_CHAT_ID=  # отдельный чат для сбоев; пусто — REMIT_TELEGRAM_CHAT_ID
REMIT_MONITOR_INTERVAL=60      # как часто проверять, секунды
REMIT_CERT_WARN_DAYS=14        # предупреждать об истечении сертификата
REMIT_SCHEDULER=true           # false — выключить фоновые задачи в этом процессе
```

Бот для Telegram заводится у @BotFather, его нужно добавить в чат
администраторов. Номер чата можно узнать через @userinfobot.
